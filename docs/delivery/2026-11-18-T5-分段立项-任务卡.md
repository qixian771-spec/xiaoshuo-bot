## 1. 背景与证据

- 立项器 `src/xiaoshuo_bot/planner.py` 的 `AutoNovelPlanner.plan_new_project()` 让模型**一次**输出整本书 JSON：`project / characters / assets / foreshadows / style_profiles / volume_cap_locks / scenes`（lv0_1 要 70～95 章；lv2_plus 要 15 章 + 100 条 `master_outline`）。
- 用真模型（Gemini 3.8 Flash，`XIAOSHUO_PLANNER_MODEL="gemini-3.8-flash-tiered(high)"`，经服务器本机 CPA）跑，3 次全失败：`outline scene: missing required field 'chapter'` 等。
- 诊断证据在服务器 `kr`（`ssh kr`）：`/root/planner-diag-20261118/`
  - `request_1.json`：当时发给模型的系统/用户提示词。提示词**只列了顶层字段名，没有任何字段格式**。
  - `raw_1.txt`：模型原始输出。`scenes` 85 条，每条只有 `public_title / emotion_polarity / summary` 3 个字段；`characters` 只有 `name / role / description`；`assets`、`style_profiles` 是对象不是列表；`foreshadows` 是字符串列表。
  - `meta_1.json`：`completion_tokens=4325`（其中推理 1836），用时 20.2s。即使格式全对，85 章 × 十几个字段也远超单次 `max_tokens=12000`。
- 现有校验失败时只把**第一个**错误回填给模型，3 次重试每次最多修一个字段，必然失败。
- 另一处冲突：立项向导（`server/wizard.py`）里模型会随手给主角起名（如「陈峰」），而立项器要求人名只能取自 `CharacterNamer` 推荐的安全名池；向导的立项要求又写着「不得改动主角设定」，两边打架。

## 4. 设计（必须照做）

### 4.1 分段流程

```
plan_new_project(...)
  ├─ 阶段 1「设定包」 bible：1 次调用（≤3 次校验重试）
  │    输出 project + characters + assets + foreshadows + style_profiles + volume_cap_locks
  ├─ 阶段 2「章纲」 scenes：每批 10 章，按章号顺序（85 章 = 9 批；lv2_plus 15 章 = 2 批）
  │    每批输入：设定包（含全部 id）、此前各章的「章号+标题+一句梗概」、本批章号范围、全书三幕位置
  ├─ 阶段 3（仅 lv2_plus）master_outline：每批 25 条，共 4 批，每条 {chapter, title, summary}
  └─ 组装成原来的 payload → 原样交给 _validate_and_write_staging() + load_project()
```

- **不准改** `_validate_and_write_staging()` 和 `loader.py` 的任何门槛（章数范围、书名 15 字、人名、连续压抑 ≤2、伏笔埋设/回收章存在等）。
- 伏笔的 `plant_chapter / due_chapter` 由设定包阶段给出；章纲每批的提示词里要列出「本批范围内必须埋设/回收的伏笔 id 与关键词」。
- 每批章纲的 `active_characters / active_assets / style_profile_ids / pov_character` 只能用设定包里已有的 id，提示词里要列出全部可用 id。

### 4.2 提示词必须给出完整格式样例

- 每个阶段的系统提示词附**完整 JSON 样例**，字段名、类型、必填项与 `loader.py`（`_parse_scene`、`load_project`、`validate_project`）及 `models.py` 中 `CharacterAnchor / AssetState / ForeshadowItem / StyleProfile / SceneOutline / VolumeCapLock` 的 `from_dict` 一致。
- 样例取值参考仓库内能通过 `load_project()` 的真实项目 `projects/baiwu_dukou/*.yaml`（该项目 `contract_track: legacy`，tomato 轨额外要求见 `validate_project` 中 `contract_track != "legacy"` 分支）。
- 样例里不得出现会被当成真内容抄进书里的具体情节；用占位说明（如 `"<本章发生的第 1 个物理事件>"`）。

### 4.3 每段校验：一次列出全部错误

- 给每个阶段写「全量错误收集器」，例如 `_collect_bible_errors(payload) -> List[str]`、`_collect_scene_batch_errors(batch, bible, chapter_range) -> List[str]`：逐条检查必填字段、枚举值、id 引用、章号连续且落在本批范围、`public_title` 不带「第X章」、人名过 `CharacterNamer` 等，**把所有问题都收进列表**，不在第一个错误处停。
- 有错误：把**完整错误列表**回填给模型，要求整批重出；每阶段/每批最多 3 次；3 次都不过 → 抛 `PlanningValidationError`，信息包含阶段名、批次、全部错误。
- 收集器只做「提前发现」，最终仍以 `_validate_and_write_staging()` + `load_project()` 为准；收集器通过而最终校验失败时，直接抛错（同样不重试整本书）。
- **禁止**：吞异常、给缺失字段填默认值冒充模型输出（`_validate_and_write_staging` 里已有的 `setdefault` 保持原样，不新增）、自动换模型、降低门槛。

### 4.4 人名冲突

- 向导确认时生成的立项要求里加一句：「向导中出现的人物姓名只是示意，正式姓名必须从推荐安全角色名池中选取，其余主角设定（身份、性格、金手指、代价、成长线）必须保留」。
- 立项器 `brief_section` 的说明同步改成上述口径。

### 4.5 确认改为后台异步 + 进度

- `POST /api/wizard/sessions/{id}/confirm` 立即返回 **202**，会话状态 `PLANNING`；在后台线程执行立项。
- 进度写进 `wizard_sessions` 新字段（例如 `progress_json`：`{"stage": "scenes", "batch": 3, "batches": 9}`），`GET /api/wizard/sessions/{id}` 返回它。
- 成功：状态 `CREATED` + `book_id`；失败：状态 `FAILED` + `error_message`（完整原因）。失败后允许老板再次点确认重试（状态 `FAILED → PLANNING`），不允许同时跑两个。
- **老库迁移**：服务器 `/opt/xiaoshuo-bot/data/matrix.db` 里 `wizard_sessions` 表已存在，`CREATE TABLE IF NOT EXISTS` 不会加列。必须在 `_init_schema()` 里用 `PRAGMA table_info(wizard_sessions)` 判断后 `ALTER TABLE ... ADD COLUMN`，并写测试覆盖「旧表结构升级」。
- 进程重启时处于 `PLANNING` 的会话：启动时改为 `FAILED`，`error_message` 写「服务重启中断了立项，请重新点确认」。不准静默丢弃。
- `wizard.js`：确认后每 3 秒轮询会话，显示「正在规划：设定包 / 章纲第 X/Y 批 / 总纲第 X/Y 批」；`FAILED` 显示完整原因与「重新确认」按钮；`CREATED` 显示书号与「去演播厅看」。

### 4.6 运行参数

- 每阶段调用用 planner 角色（`_invoke_planner`），`max_tokens` 按实测设定：设定包 ≥ 8000，章纲每批 ≥ 8000。实测若触发截断（引擎/CPA 会因 `finish_reason != "stop"` 抛 `LLMStreamTruncatedError`），**缩小批量**（如 10 → 8）而不是放宽检查，并把实测数据写进验收记录。

## 9. 铁律（违反即不通过）

- 出错就停、就报，禁止空 `except`、`|| true`、`2>/dev/null` 掩盖失败、静默默认值、假数据冒充真实结果。

- 禁止降低任何门槛（章数、书名、人名、字数、伏笔、连续压抑）。
- 删除只准挪进废纸篓/归档目录；不碰 `/opt/cli-proxy-api/auth-files/`、`/etc/xiaoshuo-bot/` 里的密钥值。
